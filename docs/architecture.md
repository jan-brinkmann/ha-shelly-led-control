# Technical decisions

## Local RPC and state

The integration uses the asynchronous `aioshelly` library that also powers Home Assistant's official Shelly integration. It opens a local Gen2 RPC WebSocket, supports Shelly's SHA-256 digest authentication, and receives device notifications without changing the device's existing outbound-WebSocket settings.

The manifest declares `shelly` in `after_dependencies` and has no direct Python requirements. Home Assistant therefore installs the library version required by its built-in Shelly integration before importing this integration, even when Shelly is not configured. This avoids installing a competing `aioshelly` version into Home Assistant's shared Python environment. The built-in integration remains optional; its device entries are not required for LED control. See [Home Assistant's manifest documentation](https://developers.home-assistant.io/docs/creating_integration_manifest/#after-dependencies).

The integration reads `PLUGS_UI.GetConfig`. `leds.mode: off` maps to a Home Assistant light state of off. In power mode, an off relay also maps to zero effective brightness and an off status light, even during night mode or before clock synchronization; the saved power brightness remains unchanged. An enabled night mode with brightness `0` also maps to off while the Shelly-local time is inside its configured window. Normal brightness `0` maps to off when night mode is known to be inactive; unknown brightness retains the enabled indication state. The light uses the same effective brightness calculation as the sensor. `PLUGS_UI.GetStatus` has no independent status values, so this is a configuration-state mapping rather than a direct measurement of emitted light. The coordinator reads `Sys.GetStatus.time`, using `unixtime` for its seconds when available, and schedules a refresh at each enabled night-mode boundary regardless of brightness. This keeps the light, brightness sensor and night-mode activity sensor current. `NotifyEvent` events reporting a `plugs_ui` `config_changed` request a refresh; component names are matched case-insensitively to accept both notification and RPC-style casing. `NotifyStatus` and `NotifyFullStatus` updates also refresh on a changed `sys.cfg_rev`, including when relay output is unchanged and no LED component event arrives. The client seeds its cached revision from the initial device status and remembers only valid nonnegative integer revisions; repeated revisions and power-only changes do not cause additional refreshes. This updates both RGB presets after edits in the Shelly web UI without manual reload or waiting for polling. See [Shelly's notification examples](https://shelly-api-docs.shelly.cloud/gen2/General/Notifications/). A five-minute refresh is retained as a fallback for missed events and direct device changes. A disconnected RPC link marks the coordinator's data unavailable so a successful refresh restores all entities even when the configuration has not changed.

For every service call, the integration reads the full `PLUGS_UI` configuration. It sends `PLUGS_UI.SetConfig` with the unchanged configuration and only a modified `leds.mode`, selected `leds.colors` RGB/brightness fields, or selected `leds.night_mode` fields. Off always writes `off`. On restores the last non-off mode observed during the current runtime; if the device starts in off mode after a Home Assistant restart, the documented stable fallback is `switch`. The night-mode switch changes only `enable`; the time entities change only the relevant `active_between` value; the night-mode brightness number changes only `leds.night_mode.brightness`. All other settings are preserved. Every successful configuration service calls `async_refresh` directly, avoiding the push refresh debouncer's cooldown so consecutive control changes immediately update all entities. Push events and scheduled boundary updates still use debounced refresh requests.

The **LED indication mode** configuration select exposes only `power` and `switch`, with translated labels matching the Shelly web UI. It changes only `leds.mode` under the shared command lock and remembers a successfully selected enabled mode for the status light's next on command. A selection enables indication from `off`. Off remains controlled by the existing status light; while off or in an unsupported mode, the selector has no current option and Home Assistant displays unknown. Selecting the already active mode skips the write. Errors preserve the previously observed mode.

The two RGB configuration lights **LED color when relay is on** and **LED color when relay is off** expose independent presets in `leds.colors["switch:0"].on/off`. They share the existing integration-owned device and have MAC-based unique IDs with `switch_on_color` and `switch_off_color` suffixes. They are available only in switch indication mode and when their respective configuration branch exists. Each light's on/off state and brightness describe its normal preset, independent of actual relay output and night mode. Missing brightness yields unknown state; missing, invalid or null RGB yields unknown color without blocking other platforms. The coordinator stores both immutable presets in its state, so color-only changes trigger entity updates even with unchanged brightness and relay output.

Home Assistant's native color picker uses `ColorMode.RGB` and RGB components from 0 to 255. Reads scale Shelly's 0–100 RGB/brightness percentages to that range; writes scale back to percentages rounded to two decimals. Color-only writes preserve brightness, even zero. Combined RGB/brightness changes use one SetConfig call. Turning a preset off changes only its brightness to zero; a bare on command leaves positive brightness unchanged or sets zero brightness to 100%. Unknown brightness cannot be enabled implicitly, but an explicit brightness can be set. Each writer checks fresh mode/configuration under the command lock, rejecting stale services after a mode change, and updates only the explicitly selected relay state's fields. It never changes relay output, the other preset, power-mode brightness, night mode or controls. Power-mode color remains managed by Shelly's firmware. See the [Shelly schema](https://shelly-api-docs.shelly.cloud/gen2/Devices/Gen2/ShellyPlusPlugS/) and [Home Assistant's light contract](https://developers.home-assistant.io/docs/core/entity/light/).

The **Normal brightness** configuration number shows `normal_brightness` independently of night-mode activity, with 0 to 100% limits and a 1% step. It writes `leds.colors.power.brightness` in `power` mode or `leds.colors["switch:0"].on/off.brightness` for the latest relay output in `switch` mode. The client validates the percentage before contacting the device and reads the configuration and relay status under the shared command lock before selecting a target. It changes only that brightness field in a deep copy, preserving the other relay state's brightness, RGB values, mode, night mode and controls. Disabled or unsupported modes, unknown relay output and malformed color branches reject writes without selecting a fallback. A missing brightness field in an existing branch can be set. The number is unavailable for `off` or unsupported modes; missing brightness or relay data is unknown. Successful writes refresh all entities from the device. The existing night-mode number keeps its unique ID and registry entry.

`leds.night_mode.active_between` is represented by two configuration time entities using Shelly's local `HH:MM` format. `leds.night_mode.brightness` is exposed as a configuration number with a range of 0 to 100% and a step of 1%. The client rejects invalid percentages before contacting the device. Changing brightness does not enable or disable night mode or change its schedule. A successful write refreshes all entities from the device, including the effective on/off state and boundary timer when brightness changes to or from zero. An omitted brightness value remains unknown until it is reported by the device or set by the user.

The **Use night mode** switch represents only `leds.night_mode.enable` and retains its existing unique ID and registry entry. The read-only **Night mode active** binary sensor represents `enable` combined with membership in the configured Shelly-local time window. Its value does not depend on brightness or LED mode. The start is inclusive, the end exclusive, and equal boundaries retain the existing all-day interpretation. If enabled night mode has no synchronized clock, activity is unknown; disabled night mode is always inactive. Both the binary sensor and the light use the same time-window calculation.

The read-only **Status LED brightness** sensor reports the effective brightness from 0 to 100%, with `SensorStateClass.MEASUREMENT` for Recorder history and long-term statistics. `off` always gives zero. In power mode, `Switch.GetStatus.output: false` also gives zero before evaluating night mode; this follows [Shelly's relay-dependent LED behavior](https://kb.shelly.cloud/knowledge-base/shelly-plus-plug-s-v2). An on relay at 0 W still uses its saved brightness and indicates zero load by green; brightness is not scaled by the measured power. Otherwise active night mode overrides the normal brightness with `leds.night_mode.brightness`, as described in [Shelly's web interface guide](https://kb.shelly.cloud/knowledge-base/shelly-plus-plug-s-web-interface-guide). Outside night mode, `power` reads `leds.colors.power.brightness`, and `switch` reads `leds.colors["switch:0"].on/off.brightness` selected by relay output. The coordinator fetches and stores relay output in both power and switch modes, including on fallback polls. Status push notifications trigger a refresh when the cached relay output or system configuration revision changes; unrelated power readings do not trigger a refresh. Missing or invalid normal brightness or relay data gives an unknown sensor value without preventing the existing platforms from loading. A positive power-mode brightness requires known relay output; a configured zero remains zero with unknown output. An enabled night-mode schedule without a synchronized clock also gives unknown brightness, unless LED indication is disabled or a power-mode relay is known to be off. The sensor calculates the brightness setting; it does not measure light output. See [Shelly's configuration schema](https://shelly-api-docs.shelly.cloud/gen2/Devices/Gen2/ShellyPlusPlugS/) and [Home Assistant's sensor documentation](https://developers.home-assistant.io/docs/core/entity/sensor/#long-term-statistics).

## Identity and coexistence

The config flow gets the MAC address from the Shelly API and formats it using Home Assistant's MAC helper. It is the config entry's unique ID and the light's stable unique-ID suffix; hostnames and IP addresses are not used as identity.

The official Shelly integration also associates its device with the Shelly MAC address. However, current Home Assistant device-registry rules scope identifiers and network connections to the config entry that owns them. A physical device supported by more than one integration has one device entry per owning config entry; another integration cannot safely add an entity to the existing official Shelly device entry. This integration therefore creates its own device-registry entry with its own domain identifier and the same normalized network MAC. This is intentional, avoids registry collisions, and leaves the official Shelly integration untouched.

## Scope deliberately deferred

The integration exposes one status on/off light, two switch-state RGB configuration lights, an indication-mode select, a night-mode use switch, read-only night-mode activity and effective brightness sensors, normal and night-mode brightness numbers, and start/end time entities. Custom power-to-color mappings, discovery and support for additional models are not implemented here.
